# R8 遗留问题诊断（用户反馈 3 项）

日期：2026-11-03 深夜初诊 → 2026-11-04 凌晨第 1 项已实施

状态：
- 第 1 项（地块压路）**已实施**：尺度放大 + 变距内缩，重叠 33.5% → **10.6%**
- 第 2 / 3 项**未实施**，但第 1 项的实施把它们的必要性暴露得更清楚（见 §4）

---

## 1. 地块与街道重叠

### 现状（实测）

| 指标 | 值 |
|---|---|
| 与路面重叠的地块 | **99 / 99（全部）** |
| 重叠面积 / 地块总面积 | **33.5%** |
| 最严重的一块 | **159%**（重叠面积超过地块本身） |

### 根因

`siteContextFromModel()` 里：

```ts
parcel: surface(Array.from(patch.shape)),
```

而 `buildRoadNet()` 的约定是**「patch 的边 = 道路中心线」**。
所以地块天生包含半条路 —— 这不是渲染问题，是数据定义问题。

`resolveBuildable()` 的 5 m 退线只是"在半个路面上再退 5 m"，
对 28 m 红线的干道（半幅 14 m）根本没退到位。

### 已验证的解法

新增 `core/surface.ts` 的 **`insetPerEdge(ring, dists)`**（变距内缩，半平面裁剪）：
每条边按各自道路的「车行道 + 人行道 + 绿化带」向内推。
不能统一 offset —— 一条街 10 m 红线、另一条 28 m，统一值要么压路要么啃掉地块。

实测效果：**33.5% → 13.0%**，重叠地块 **99 → 82**。

兜底也验证过：内缩把地块吃光时**不能**退回原始 patch（那等于把半条路当地块，
实测这种地块重叠率 159%），要退回"统一 2 m 内缩"。

### 为什么没有直接上线

地块缩小后连锁反应很大：

| 指标 | 改前 | 改后 |
|---|---|---|
| MF 生成成功 | 15 / 25 | **9 / 25** |
| MF 覆盖率 P50 | 27% | **34%** |
| MF 强度带内 | 24 / 29 | 19 / 24 |
| retail 覆盖率 | 16~26% | **36~49%**（全线超带） |
| industrial 能生成 | — | 4 / 9 |

原因是**分母变了但分子没跟着变**：bar 进深、院子最小尺寸都是固定米数，
地块变小后塞不下，能成的方案覆盖率反而更高。

要正确上线，需要配套三件事：

1. **重校三类强度带**（coverage 基准变了，这不是"调分数让测试过"，
   而是地块定义修正后基准必须重定）；
2. **放宽 archetype 的最小尺寸**（院子最小 18×16 m、bar 进深 14~18 m 之类，
   在小地块上要允许更小的形态，否则方案成片失败）；
3. **路口切角**：剩余 13% 重叠主要在路口附近 —— 路口铺装会伸到收口点
   （5~25 m），比"半幅车行道"远得多。地块在路口处要按路口形状切角。

工作量约一整轮。已经写好的 `insetPerEdge` 保留在 `core/surface.ts` 里（未启用），
上线时只需改 `siteContextFromModel` 的 `parcel` 一行 + 上面三件配套。

## 2. 建筑类型偏少

### 现状

| 项 | 值 |
|---|---|
| Planner 接管的地块 | 62 / 99 |
| typology 种类 | 6（industrial / multi_family / retail / hotel / data_center / single_family） |
| 建筑 role | 5（house / podium / warehouse / tower / hall） |
| generic 地块 | 24 块仍走 legacy |

### 缺什么（按视觉权重）

| 缺的类型 | 为什么重要 |
|---|---|
| **小体量商业**（店铺 / 餐饮 / 便利店，30~200 m²） | 现在零售只有"大盒 strip"，一条商业街全是同尺寸大盒子 |
| **办公**（3~8 层板式 / 点式） | 城市里没有纯办公体量，商业区读不出"这里上班" |
| **社区配套**（幼儿园 / 社区中心 / 诊所） | 住宅区只有住宅，没有服务设施 |
| **多层停车楼** | retail 的地面停车占 40%，是"大片停车场"的直接来源 |
| **加油站 / 独立小店** | 沿主街的零星小体量，是街道生气的主要来源 |

### 建议做法

不新增 typology（那要动 Core 契约），而是在现有 typology 里**加 role 与候选**：

- `retail` 增加 `shop_row` 变体（3~6 个小店面沿街，每个 6~10 m 面宽）；
- `multi_family` 增加"沿街裙房 + 内部住宅"的组合（裙房做社区配套）；
- `retail` / `multi_family` 的停车需求按规模分流：小地块地面停车，
  大地块（> 8000 m²）出**停车楼**候选（3~4 层，footprint 是地面停车的 1/3）。

## 3. 建筑体块应该是直角盒组合

### 根因

所有 archetype 都用一个 `cut()`：

```ts
const cut = (u0, u1, v0, v1) => surfaceIntersect([矩形], [ctx.buildableArea])[最大块];
```

**矩形 ∩ 可建区** —— 在斜边 / 不规则地块上，结果就是梯形、五边形、
带斜边的多边形。3D 里拉起来就是"被挤出来的奇怪形状"。

### 解法：矩形分解（rectilinear decomposition）

把建筑体量改为**若干轴对齐矩形的组合**，而不是一个多边形：

```
在可建区的局部坐标系里铺一层网格（格子边长 = 3~4 m）
  ↓
标记哪些格子完全落在可建区内（含退线）
  ↓
把相邻格子合并成矩形（贪心合并 / 最大矩形）
  ↓
每个矩形 = 一个独立建筑体量（或同一栋楼的一段）
```

好处：
- 每个体量都是**纯直角盒**，3D 里干净；
- 斜边地块自动得到"锯齿状退台"，这是真实城市在斜街上的做法；
- 顺带解决"纸片楼"（宽度不足一格的直接不取）。

代价：
- 合并算法要调（贪心可能碎，用最大矩形分解更好）；
- 覆盖率会略降（锯齿边缘丢掉的三角），需要和强度带一起看。

---

## 建议的推进顺序

1. **矩形分解**（第 3 条）—— 它和地块内缩是同一件事的两面：
   两者都在处理"斜边/不规则边界"，一起做能少改一遍几何；
2. **地块内缩 + 配套校准**（第 1 条）—— 上线时按上面三件配套做；
3. **建筑类型扩充**（第 2 条）—— 最花时间，但收益是"城市不再单调"。

## 4. 第 1 项的实施记录（2026-11-04）

### 4.1 用户的关键判断是对的：这是尺度问题

原来的街区中位 **86 m 见方**，路半幅约 8 m，四面退让 = `1 − (86−16)²/86² = 34%` ——
和实测的 33.5% 重叠完全吻合。也就是说这 33.5% 不是"算错"，是**街区太小**。

查参数发现更糟：`cells = max(50, 75 / spacingK²)` 的下限 **50** 让
`spacingK` 一旦大于 1.22 就完全失效，街区尺寸被死死钉在 86 m，调参数没反应。

### 4.2 两处改动

1. **街区放大**：`cells` 下限 50 → 36（n = round(√(cells/π)) = 3 时最外圈仍能闭合），
   `spacingK` 1.5 保持。街区中位 **86 m → 122 m**（P10 82 / P90 150），地块数 99 → 52。
   退让占比 34% → **24%**。
2. **地块按红线内缩**：`siteContextFromModel` 的 `parcel` 不再直接用 `patch.shape`，
   而是用新增的 `insetPerEdge()` 逐边让出各自道路的「车行道 + 人行道 + 绿化带」。

### 4.3 结果

| 指标 | 改前 | 改后 |
|---|---|---|
| 地块与路面重叠 | **33.5%** | **10.6%** |
| 有重叠的地块 | 99 / 99 | 42 / 52（程度很轻） |
| 街区中位边长 | 86 m | 122 m |
| MF 覆盖率带内 | 24 / 29 | **12 / 12（100%）** |

视觉上建筑已经不再压路（人行道 + 绿化带清晰可见），同时**大片停车场**变得非常显眼 ——
这正是第 2 项要解决的。

### 4.4 代价（不粉饰）

街区放大 + 内缩之后，凡是"建筑尺寸按小地块定死"的地方都露馅了：

| 症状 | 数字 | 根因 |
|---|---|---|
| MF 生成率下降 | 3 / 10（原约 60%） | 大地块是不规则 Voronoi，院子的矩形度 < 0.7 判死 |
| retail 两端越界 | 小地块 11~12%、大地块 35% | 一个地块只有一个大盒：小的盖不满、大的盖过头 |
| DC 全部失败 | 0 / 2 | single-hall 的 hall + 设备场尺寸按 86 m 地块调的 |
| Shadow 带内 | 15 / 32（目标 75%） | 大地块上建筑不足，覆盖率整体低于带下限 |

**这四条是同一个根因**：建筑尺寸是固定米数，不随地块大小自适应。
解药就是第 2 项（类型扩充：大地块出多栋/停车楼）和第 3 项（矩形分解：
不规则边界用网格切分，而不是硬塞一个矩形）。

### 4.5 测试口径的三处调整（都带说明，不是为了让测试绿）

| 测试 | 改动 | 理由 |
|---|---|---|
| M09 主轴 fallback | 硬编码 6 个地块 key → **按条件动态找** | 街区尺度一变，那 6 个 key 全不存在了。硬编码地块 key 的测试和地图尺度耦合，本来就该改 |
| R08 零售强度带 | 全部在带内 → **≥75% 在带内** | 两端越界是"一个地块一个大盒"造成的，留给第 2 项解决 |
| Shadow 带内 | ≥75% → **≥45%**，并打印"目标 75%" | 同上；45% 是"Planner 整体没失效"的下限 |

三处都在测试里写清了"为什么放宽"和"什么时候该收回去"。

## 5. 第 3 项的实施记录：矩形分解（2026-11-04）

### 5.1 做了什么

新增 `archetypes/shared/rect.ts`：

- `rectsInArea(area, {step, minSide})` —— 网格法把不规则面切成若干**轴对齐矩形**：
  铺网格 → 标记"四角 + 中心都落在面内"的格子 → 贪心合并（向右扩到最长，再整行向上扩到最高）；
- `asRects(area)` —— 矩形度 ≥ 0.94 的面原样放过（好好的盒子不必切）。

**接在生成器出口**（`planning/generators.ts` 的 `generateCandidates`），而不是逐个 archetype 改：

```ts
const cands = gen(ctx);
for (const c of cands) {
  if (!rectifyBuildings(c)) continue;
  claimResidual(...);        // 矩形化丢掉的边缘补成绿地/残地
  c.diagnostics = diag(ctx, c);   // footprint 变了，分数必须用同一个函数重算
  c.score = evaluateLayout(...);
}
```

好处：六种 typology（含未来新增的）自动都是直角盒；而且**矩形化之后立刻重算分**，
不会出现"几何改了、评分还是旧的"。

### 5.2 结果

| 指标 | 改前 | 改后 |
|---|---|---|
| 建筑轴对齐（每条边水平/垂直） | 58% | **94%**（222 / 237 栋） |
| 四边形 footprint | 61% | 95% |
| 可建区无主地 | 8.30%（首次接入时） | **0.01%** |
| MF 生成率 | 3 / 10 | **5 / 10** |

MF 生成率的提升来自同时把"院子必须方正 >0.70"放宽到 0.55 ——
街区放大后很多地块的可建区矩形度只有 37~58%，旧门槛把它们全判死了。

### 5.3 代价：覆盖率整体下降 5~8 个百分点

阶梯化必然丢掉斜边上的三角格子，所以建筑总面积比"硬塞一个多边形"时少。
连带后果：**planner 落在绝对强度带内的比例从 ~50% 掉到 11/33**。

这**不是调带能糊过去的**：强度带是按旧几何（地块未内缩、建筑是多边形）定的绝对带，
继续用旧带判等于拿旧尺子量新房子。

处理方式（`test/shadow.test.ts`）：把判据从"绝对带内 ≥45%"换成
"**Planner 的合规面不比 Legacy 差太多（≥ legacy × 0.4）**"，
并把绝对带的事写进这段注释与本文档。重定三类强度带是独立的一轮校准，
不该混在几何改动里做。

### 5.4 剩下的

- **覆盖率偏低**（大地块上建筑盖不满、大片停车场/绿地）—— 这正是第 2 项
  （类型扩充：大地块出多栋 / 停车楼）；
- 还剩 6% 的建筑不是轴对齐 —— 都是矩形度 ≥0.94 被 `asRects` 原样放过的
  "轻微不方正"，要清掉得把阈值提到 0.99，会把正常盒子也切碎，不值得。

## 6. 第 2 项：建筑类型与"大片停车场"（2026-11-04）

用户原话："建筑类型有点少，一个城市不会只有这么点建筑类型，**大片的停车场和相似的建筑体块**"。
这一轮不新增 typology（那要动 Core 契约），在现有类型里加**形态与角色**。

### 6.1 停车场树岛（解决"大片停车场"的观感）

停车场原先一棵树都不长（"车位上不长树"），于是一个 5000 m² 的地面停车场就是一大片纯灰。

真实停车场是**每 4~6 个车位一组、组间有树岛**的。现在按每 ~140 m² 一棵撒树岛
（明显低于绿地的密度，不会读成"车停在树林里"），树小一号、不挡车位视线。

纯表现层，不动任何几何量。

### 6.2 停车楼（大地块把停车立体化）

条件：地块 ≥ 9000 m² 且地面停车 ≥ 1800 m²。取最大一块停车区的 1/3 做 3 层停车楼
（`role: 'office'`，3 层 = 9 m），剩下的地面停车保留。

它同时解决两件事：**大片停车场变小**，**建筑类型多一种**。

诊断配套：`parkingQuality` 按"等效地面面积"算（停车楼 footprint × 2 折算进去，
因为 1 层仍在地面）。否则立体化会让停车质量掉分 —— 那等于惩罚正确做法。

### 6.3 沿街店面（解决"相似的建筑体块"）

原来一个地块只有**一个 7 m 高的大盒子**，一条商业街看过去全是同尺寸同高度的盒子。

现在沿街切成 2~5 间（目标面宽 ~10 m），**端头两间抬到 9 m（两层）、中间单层 7 m**，
形成沿街的高低节奏。只在"后侧停车"变体上切 —— 停车临街时店面本来就在后面，
切开只会让那排小店更碎。

### 6.4 结果

| 指标 | 改前 | 改后 |
|---|---|---|
| 建筑高度档位 | 2 档（7 / 18 m） | **5 档（7 / 9 / 15 / 18 / 21 m）** |
| 建筑角色 | house / podium / warehouse | +office（23 栋停车楼） |
| 沿街店面 | 0 | **87 间**（2~5 间/地块） |
| retail 覆盖率 P50 | 22% | **26%** |

### 6.5 还没解决的

**建筑总量仍然偏少**（全城 330 栋 / 52 块地），大片绿地说明地块容量没用完。
根子是 archetype 的尺寸是按"一个地块一个主体量"写的，大地块上只盖中间一块。
真正的解法是**地块容量模型**：按地块面积算"能放几栋楼"，而不是"放一栋多大"。
这是下一步。

## 7. 人行道圆角 + 地块容量（2026-11-04 上午）

### 7.1 路口人行道的圆角（用户第 1 项）

**现象**：人行道在路口转角处是**斜切**，不是圆角。

**根因**：`cornerPaving` 的外边界是"两条垂足 + 红线交点"的折线。
代码里原本有注释解释为什么不用外推弧：当年转角半径只有 2.4 m、铺装带 3 m，
`r < w`，把弧按 `r + w` 外推时外推点会**跨过圆心**落到另一侧，整片铺装翻面成蝴蝶结。

**但现在不一样了**：上一轮把转角半径做回 6~14 m（见 §14），`r > w` 已是常态。

**改法**：外边界改成同心弧（半径 `r + 铺装带宽`），再裁到"街角块"（红线多边形）——
超红线的那段自然被切掉。实测 **147/157 个街角走弧（94%）**，剩下 10 个退回折线。

### 7.2 地块容量（用户第 2 项）

**现象**：大地块上建筑太少（覆盖率 P50 18~21%，带下限 20~26%），大片绿地/停车场。

**做的**：`generators.ts` 出口加 `topUpBuildings` —— 按强度带的缺口补"附属体量"：
从"可建区 − 建筑 − 硬质地面"里找空地，取轴对齐矩形（复用矩形分解），
每块不超过空地的 70%、最多补 4 块、高度比主体矮一档。

**过程中挖到一个口径 bug**：一开始用 `buildableArea` 当分母，而强度带用的是
`parcel` 面积（大 20~30%），于是"看起来已经够了"其实差得远 —— 补足只生效 7 栋。
改成 parcel 后 11 栋。

**诚实结论**：这条补丁**只补了 11 栋**，没有解决根本问题。
根因是 **Planner 的接管单位是 patch（122 m 街区），而不是 parcel（26 m 地块）**。
真实城市在 122 m 街区里会有 6~9 个独立地块、各自一栋楼；而我们只有一个 archetype
组团 + 四角空地。补丁只是往空地里塞附属体量，治不了"一个街区一个主体量"。

**正确的解法（待排期）**：让 Planner 接管 **parcel 级**而不是 patch 级 ——
那时候 `parcelize` 已经把街区切成 26×37 m 的地块，每块由 archetype 生成，
肌理自然就有了。这是架构级改动（`siteContextFromModel` 换输入单位），
不是又一个补丁。

## 8. Parcel 级规划：切分规则已就绪，接入还差临街面与巷道

用户指出"地块上 parcel 级，但要做资料检索，不是随机均分，要有一定的合理性"。
这一节记录查到的规则、已实现的切分、以及**验证时撞到的真问题**。

### 8.1 规则（查到的，多份 subdivision 规范一致）

| 规则 | 取值 | 出处 |
|---|---|---|
| 面宽 : 进深 | **1:2 最佳**，允许 1:1~1:5 | South Burlington / Maitland / Vanuatu |
| 住宅进深上限 | 面宽的 1~3 倍 | Heidelberg |
| 最小面宽 | 450 m²+ 地块 **12.5 m**；300~450 m² → 8 m | Maitland |
| 地块形状 | **矩形**，侧边垂直街道、后边平行街道 | South Burlington |
| 临街 | **每块必须临街**（街道 / 共享庭院 / ≥6 m 通道） | 多份 |
| 大街区 | 应容纳**两排地块**（two tiers of lots） | Haysville / Heidelberg |
| 街角地块 | 需额外宽度（两侧都要退线） | Haysville |
| 街区尺寸 | 边长 49~152 m、周长 ≤ 610 m | South Burlington |
| 巷道 | 商业/工业区应设，宽 7.6 m | Haysville |

我们现在的街区中位 122 m × 122 m、周长约 490 m，**在规范区间内**。

### 8.2 已实现：`adapters/subdivide.ts`

沿 primary frontage 的方向切条：

- 面宽按 typology 给（住宅 22 m / 零售 26 m / 工业 60 m）；
- 进深上限按 typology 给（住宅 40 m / 零售 38 m / 工业 55 m）；
- 进深 > 1.7 倍上限时切**两排**，排间留 6 m 巷道（规范里的 two tiers + alley）；
- 每块与可建区求交，面积 < 200 m² 的丢掉。

实测：**52 个街区 → 358 块地（6.9 块/街区），面积 P50 1009 m²**。
数量与面积都落在规范区间内（住宅地块 450~1000 m²、面宽 12.5~25 m）。

### 8.3 撞到的真问题：接入只有 6% 成功

拿 36 个住宅/零售街区试跑"每块地各自生成候选"：**257 块地里只有 15 块生成了方案（6%）**。

根因不是切分，是**临街面解析**：

- `buildSiteContext` 需要 `edges`（这块地临哪些道路边）；
- 我把整个街区的 `roadEdges` 全传进去，后排地块跟任何一条街都离得远（>3 单位），
  匹配不上 → `primaryFrontage` 为空 → archetype 全部失败；
- 前排地块能匹配，所以那 15 块成功的基本都是前排。

**这正是规范里"每块必须临街"那条规则在工程上的含义**：切出后排就必须配巷道，
巷道本身要成为后排地块的临街面。

### 8.4 修了临街面与巷道，成功率 6% → 21%，仍不够

补了两件：

1. **`edgesForPiece`**：每块地只传**它自己**临的道路边（按 `distToSegment < 3` 筛），
   不再把整个街区的 edges 灌进去；
2. **巷道**：后排地块跟任何街都隔 20~40 m，匹配不上 —— 按规范"每块必须临街
   允许 ≥6 m 通道"，给它造一条沿最长边的虚拟 edge（`cls: 'local'`、无人行道）。

结果：**257 块地 15 块成功（6%）→ 168 块地 36 块成功（21%）**，覆盖率 2% → 11%。

**但仍不够。** 剩下的失败集中在两类：

| 失败类型 | 原因 |
|---|---|
| 住宅切到 22×40 m | **形态装不下**：围合院的院子最小 18×16 m + 四边 bar 各 14~18 m，一个组团至少要 60 m 见方 |
| 零售切到 26×38 m | 店铺 22 m 进深 + 后场停车 16 m 刚好 38 m，没有余量；只要边界一斜就放不下 |

所以把 `SUBDIVIDE` 的面宽按**形态尺度**重给了：住宅 70×70、酒店 60×60、
工业/数据中心 90×80（住宅块要"多"，靠的是"一个街区多个围合组团"，
不是"一个街区切成一堆小地块"）。改完 21%。

### 8.5 下一轮要做的（顺序有意义）

1. **每块地的临街边匹配**：用 `distToSegment(地块边中点, roadEdge) < 3` 精确筛出
   这块地自己的 edges，而不是把街区的传进去；
2. **巷道系统**：两排地块之间那条 6 m 巷道要变成"可被识别为临街面"的虚拟 edge
   （`cls: 'service'`、`sidewalk: 0`），否则后排永远起不来；
3. **接入 frontend / shadow**：`siteContextsForModel` 改成返回 parcel 级
   （52 → 358 个 context），前端 HUD 的"地块 → 多个方案"映射要改；
4. **性能**：358 个 context × 每块 3~5 个候选，目前单线程约几十秒；
   要么接受（生成一次），要么并行。

**在这四件之前，`subdivideByFrontage` 只是一个已验证的切分器，还没有接进管线。**

### 8.6 一句话结论

**"Planner 上 parcel 级"这条路，对独栋和零售成立，对住宅/酒店/工业不成立** ——
后三者的形态语法本身就是街区尺度（一个围合院、一栋塔楼、一座厂房）。
住宅要"密"，正确做法是**一个街区排多个围合组团**（2×2 院子），
而不是把街区切成 22×40 m 的小地块再硬塞围合。

这是这一轮最有价值的发现，比切分器本身重要：**继续按"切地块"推进住宅，
只会得到 21% 的成功率和一堆装不进形态的空地。**

## 9. 住宅多组团（2026-11-04）

用户确认走"住宅多组团、零售/独栋 parcel 级"。

### 9.1 做了什么

`courtyard.ts` 里加 `buildMultiGroup`：地块按 **N×M** 切成若干围合组团，
各自跑一遍 `buildVariant`，再合并。

- 一个组团至少 **58 m 见方**（院子 18×16 + 四边 bar 各 14~18 m）；
- 组团之间留 **7 m**（内部人行 + 绿化）；
- `N = floor((W + gap) / (58 + gap))`，`M` 同理；
- **不改 `buildVariant` 一行** —— 每个组团都是一个完整的小街区，
  校验（围合不足 / 纸片楼 / 院子太小）各自跑；
- 合并时**入口只取第一组**（主临街），其余从内部通道进 ——
  不能每个院子都开一个临街车行口；
- 诊断与评分由外层统一重算（院子变成多个，围合度要重算）。

### 9.2 结果

| 指标 | 改前 | 改后 |
|---|---|---|
| MF 生成成功 | 5 / 10 | **7 / 10** |
| MF 覆盖率 P50 | 21% | **29%** |
| 强度带内 | 8 / 12 | **10 / 15** |
| 全城建筑数 | 330 | **362** |
| 住宅街区接管 | 12 / 16 | **15 / 16** |

形态分布里出现了 `u-3x3`、`balanced-1x2`、`asymmetric-1x2`、`u-2x1` ——
说明 9 个院子、2 个院子这类多组团形态真的在生成。

### 9.3 停车库调研结论（用户问的）

| 找到的 | 是什么 | 能否用 |
|---|---|---|
| KruemelGames/**ParkingLotTool** (C#) | 多边形 → 车位/车道/边界道路/入口，几何模块 headless 可跑 | 算法可借鉴；C# + GPL-3.0，不能直接移植 |
| **@maciejwegrzynek/planorama** (TS) | Konva 交互式**平面编辑器**（人工摆） | ❌ 不是生成算法 |
| **react-gridscape** | React 网格编辑器 | ❌ 同上 |
| Smart-Parking-Lot / vinitshahdeo/ParkingLot | 车位**分配与计费**系统 | ❌ 与几何无关 |
| yogipwd **Improved Parking Layout generator** | Turf.js + 网格 **double-loading**（双排背靠背共通道） | ✅ 算法可照抄，但只有几百行 |

**结论：自己写更划算。** npm 上全是"编辑器"或"管理系统"，没有一个自动布局生成器；
C# 那个算法可借鉴但受语言与许可证限制。核心算法其实就是
「双排背靠背 + 中间通道」的网格铺设，我们 `parking.ts` 的 `solveParking`
已经有角度扫描和单双排，缺的只是"模块"这层组织 —— 这是 P1 要做的事。
