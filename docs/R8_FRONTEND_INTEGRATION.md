# R8 · Frontend Product Integration

> 这份文档记录的是**"发动机接到产品上"**这一步：Planner 的完整链路第一次进入
> 你每天实际用的那个前端界面。之后的每一次优化都能立刻在画面上看到。

---

## 1. 前端真实入口在哪

先确认了"按钮最终调用的是谁"，才动手改：

```
index.html
  └─ src/ui/app.ts            ← 主界面（三栏：左显示控制 / 中画布 / 右生成参数）
       ├─ regenerate()         ← "重新生成"按钮
       │    └─ model.generate() （城市本体，不含地块内容）
       └─ view2d / view3d
            └─ src/scene/build.ts :: buildScene(model, opts)   ★ 唯一出口
                 └─ 2D（view2d.ts）/ 3D（view3d.ts → build3d.ts）/ GLB 导出
```

**关键结论**：`buildScene()` 是 2D / 3D / GLB 三者的唯一出口，
而且它的第 3 步"地块内容"正是 legacy 链路（`ModernWard.lot`）。
所以接入点只有一个：`buildScene()` 里换成 Planner 的产物，三条渲染路径自动一起变。

**红线落实**：`realizeSitePlan()` 产出的特征**直接进 Scene**，
被接管的地块不再经过 `ModernWard.lot` 那条 legacy 规划逻辑 ——
测试用**几何归属**（质心落在这块地里）判定"场景里的实体是否全部来自 planner"，
不是靠名字（legacy 的实体名在不同地块之间是重复的，靠名字会误判）。

---

## 2. 三态运行模式

顶栏新增一组切换（`index.html` 的 `.modes`）：

| 模式 | 渲染 | 用途 |
|---|---|---|
| **Legacy** | 全部走 legacy（默认，行为不变） | 基线对比 |
| **Planner** | industrial / multi_family / retail 三类由 Planner 接管，其余仍 legacy | 看真实产出 |
| **Shadow** | 渲染仍是 legacy，Planner 的方案叠成**红色虚线轮廓** | 一眼对比两套 |

URL 参数 `?mode=planner` / `?mode=shadow` 可直接进入（截图 / 手测用）。

### Shadow 模式的语义

主场景 = legacy（一个字节都不改），Planner 的建筑画成红色虚线轮廓、
Planner 的地面画成淡红色虚线。因为不填色，legacy 的实体形态仍然可读，
Planner 的体块像投影一样浮在上面 —— 这是"两套方案并排看"最省事的实现。

## 3. Planner Mode 的链路（严格按要求）

```
Parcel
 → siteContextFromModel()      （src/town/planning/adapters/model.ts）
 → generateCandidates()         （src/town/planning/generators.ts，按 typology 路由）
 → selectBestCandidate()        （src/town/shadow/runner.ts，显式选优 + margin）
 → realizeSitePlan()            （src/town/realize，忠实落地）
 → Scene 特征
 → 现有 2D / 3D Renderer
```

`generateCandidates()` 是新抽出来的**共享路由表**（`planning/generators.ts`）——
之前映射表写在 `shadow/runner.ts` 里，前端若照抄一份就会变成两份真相，
Shadow 报的数和前端看到的数会对不上。现在两边共用同一个。

## 4. 第一批只接三类

export const PLANNER_ENABLED_TYPOLOGIES: SiteTypology[] = ['industrial', 'multi_family', 'retail'];

## 8. R8 Visual Review（表现层，已落地）

接线做完之后做视觉复核。**全部是表现层的事，不碰任何规划几何与评分**。

### 8.1 诊断（先量，再改）

| 要素 | legacy | Planner（改进前） | 问题 |
|---|---|---|---|
| 墙体 | concrete 255 / panel 97 / glass 33 | concrete 145 / stone 38 / panel 6 | **wallGlass 归零** —— 全城一个色调 |
| 树 | 3639 | 3035 | Planner 接管的地块**内部一棵树都没有** |
| 院子 | — | stonePave 大片浅灰 | 和屋面 roofLight 几乎同色 → 读成"空地" |
| 建筑厚度 | 小房子自带颗粒感 | 大板楼是一块平色 | 没有厚度线索 |

### 8.2 四项改动

**① 地块内配景（`src/town/realize/scenery.ts`，新增）**

Planner 接管的地块走的是另一条链，`modern.ts` 那套地块内部配景不会跑，
于是院子是空的。补一个 `realizeScenery()`：读 Candidate 已经定好的
Ground Program（courtyard / landscape / amenity / landscape_buffer…），
按程序撒树。仍然是纯转译 —— 不决定"哪儿该有树"（Planner 已经用 program 标出来了），
只把这些 program 翻译成看得见的树。

撒点用「固定网格 + 抖动」，抖动量由 `candidate.id` 的哈希决定 → 确定性。
并且避开**建筑 footprint、车位、货场**（车位上不长树）。

实测：树 3035 → **3291**（+256）、针叶 173 → 330、小树 37 → 134。

**② 建筑外观按 typology 分层（`TYPOLOGY_APPEARANCE`）**

legacy 链里住宅是 `brick / concrete 随机`、板楼是 `concrete / panel 随机`、
塔楼是玻璃幕墙 —— 于是俯视图上**一眼能读出这是住宅区还是商业区**。
Planner 链早期把 `house` 固定成 wallConcrete，全城一个色调（"素白大盒子"）。

现在每个 typology 有一组墙/屋面候选，按建筑序号确定性交替：

| typology | 外观 |
|---|---|
| multi_family | 砖红 / 涂料交替，平屋顶 |
| retail | 玻璃幕墙为主 |
| industrial | 金属面板 / 混凝土 |
| hotel / dc / single_family | （暂未接入，但表已备好） |

实测：wallBrick 0 → 65、wallGlass 0 → 27、roofFlat 0 → 29。

**③ 院子材质：stonePave → 草坪**（第一版用 grassLight，后来在 §10 改成 lawn）

`stonePave`(0.757) 和 `roofLight`(0.615) 在俯视图里几乎同色，
一大片院子读起来像"这块地空着"。换成修剪草坪之后，
院子 / 绿化(grass) / 铺装(paver) 三层一眼分得开。

**④ 2D 建筑加假投影 + 轮廓随体量加重（`view2d.ts`）**

同样是屋顶色，大板楼读起来像"一块铺装"，小房子才像"房子" —— 差的是厚度线索。
沿右下压一层半透明深色，体块立刻立起来。纯表现层，不碰几何。

## 9. 地面归属与几何可靠性（P0 修复）

这一节记的是 R8 收尾时挖出来的**最严重的一个问题**，它的表象是"视觉脏点"，
根因却在几何内核。

### 9.1 现象：可建区里有一片没有主的地

量"可建区里有多少面积既不在 ground 也不在建筑里"：

| typology | 无主占比（修前） |
|---|---|
| industrial | **20.4%** |
| retail | 9.3% |
| multi_family | 3.6%（另有 3 块整块 100%） |

这些地在 Scene 里没有任何 ground program，2D 上就是一片纸面底色，
读起来像"这块地没规划完"。

### 9.2 根因：布尔运算静默失败 + 残地只认领最大一块

两层问题叠在一起：

**① 残地只认领最大一块。** 六个 archetype 都是这么写的：

```ts
const biggest = rest.reduce((a, b) => surfaceArea(a) >= surfaceArea(b) ? a : b);
if (surfaceArea(biggest) > buildable * 0.01) add('residual', biggest);
```

新月形地块上，剩下的是**两侧两条月牙**，只认领大的那条，小的直接丢掉。

**② 更糟的是 `surfaceSubtract` 会静默返回整块输入。**
polygon-clipping（martinez 实现）在"减数与可建区边界相切 / 顶点几乎重合"时抛

```
Unable to complete output ring starting at [5.94, 6.79]. Last matching segment found ends at [...]
```

而 `surfaceSubtract` 有 `catch { return as }` 的兜底 —— 于是
`subtract(可建区, 已用地)` 返回**整块可建区**，调用方把它标成 `landscape`，
一张 4928 m² 的假"绿地"盖住了整块 4928 m² 的地。**2D 上完全看不出来**，
因为那就是地块底色；只有"无主面积"这个度量能发现。

### 9.3 修法（三层，全在 Core 与 archetype 内，不改契约）

| 层 | 做法 |
|---|---|
| 输入 | 送进布尔运算的坐标**量化到 1e-6 世界单位**（≈7 μm）。martinez 对 1e-15 级差异极脆，量化把它消掉 |
| 退化 | 批量 difference 失败时**降级为逐块减**：每次只面对一个减数。宁可少切（残地偏少），也绝不返回整块（残地 = 整块在视觉上是假满铺） |
| 可观测 | 新增 `geometryFailures` / `resetGeometryFailures()`。`catch` 里计数，测试断言三个计数为 0 —— 兜底不再无声 |

再加 `claimResidual()`（`archetypes/shared/claim.ts`）：**全部残地按面积分档认领**
（≥0.8% 给绿地 program、≥0.15% 给 residual、更小丢弃），六个 archetype 共用。
typology 由 archetype **显式传入**，不从 `ctx.typology` 推导 ——
DC 的测试 fixture 用了 `use: 'industrial'`，靠 ctx 推导会把工业的
`landscape_buffer` 漏进数据中心的白名单校验里。

### 9.4 结果

| 指标 | 修前 | 修后 |
|---|---|---|
| 无主占比 | 5.73% | **0.02%** |
| 布尔静默失败 | union 4 / subtract 3 / intersect 4 | **0 / 0 / 0** |
| 整块无主的地 | 4 块 | **0 块** |
| 有方案的 MF 地块 | 26 | **29**（3 块原本生成失败的地现在成功） |

### 9.5 一次判断失误（记录下来）

中途我以为"建筑在 Planner 模式下还是浅灰、没变深"，连续调了两轮屋顶色。
实际采样截图像素才确认建筑是 `rgb(97,90,78)`、院子是 `rgb(163,176,116)` ——
**颜色早已正确，是缩略图的主观感受骗了自己**。

教训：涉及"颜色够不够对比"这种判断，**采样像素，不要靠看图**。
这也是为什么下面 §10 的配色结论都带具体 rgb。

## 10. 地面与建筑的配色层次（可复用的结论）

`palette.ts` 的值是 **sRGB 0~1**，`css()` 直接 `*255`，**不做线性→sRGB 转换**。
（注释里写的是 sRGB，之前有人按线性值估算亮度，估出来的对比度全是错的。）

按亮度排出的可用层次：

| 档 | 材质 | 用途 |
|---|---|---|
| 0.76 | `stonePave` | 入口前场 |
| 0.70 | `paver` | 会客场地、人行 |
| 0.60 | **`lawn`（新增）** | 围合院子的草坪 |
| 0.52 | `gravel` | **工业缓冲带**、残地 |
| 0.40 | `grassDark` | 地块边缘绿化 |
| 0.40 / 0.30 | `roofFlat` / `roofDark` | 住宅屋面 |
| 0.27 | `asphaltLot` | 停车 |

三条改动：

1. **院子用 `lawn`（低饱和浅绿），不用 `grassLight`。**
   院子占围合式住宅地块的 **67%**，饱和草绿铺满之后整座城读起来是
   "公园里散着几栋楼"，不像规划图。专业总图上的草坪是浅而灰的绿。
2. **工业缓冲带用 `gravel` 而不是草。**
   工业地块的 `landscape_buffer` 现在占 23%（全认领之后），给草会把整片工业区染绿；
   真实的工业场地边缘本来就是碎石/杂草。
3. **住宅屋面压到 `roofDark` / `roofFlat`。**
   2D 用 roofMat 填充，所以"屋顶浅"等于"楼是白的" —— 这正是用户说的"素白大盒子"。
   压深之后，浅绿院子上的深灰条 = 楼，figure-ground 才立起来。

### 10.1 遗留（已由 §11 解决）

院子当时是一整块纯色 + 几棵树，没有步道连接各栋楼入口 —— 见 §11。

## 11. 院子内部结构（archetype 几何）

§10 结束时院子还是一条"绿毯"。这一节补上它内部的骨架 —— **这是 archetype 层的
改动**，会改变几何与评分，和前几节"只动表现层"的性质不同。

### 11.1 做了什么

| 改动 | 说明 |
|---|---|
| **院内十字步道** | 主步道 5 m，从临街（或门洞）贯穿院子到后侧 bar；院子净宽 ≥26 m 且进深 ≥22 m 时再加横向支路 4 m。草坪被切成 2~4 块 |
| **临街 bar 开门洞** | 5 m 门洞（面宽 ≥24 m 才开）。**这是修一个真缺陷**：bar 占满整个面宽时，院子被它和街道完全隔开，平面上根本走不进去 |
| **前场对齐门洞** | 前场中心改用院子中心（`entryU`），不再用地块中心（`u0+0.5W`）。两者在两侧 bar 不等宽时会错开一格 |
| **前场填满门洞** | 深度从 `0.6×frontD` 改成 `frontD`：门洞里原来剩一段没有 program 的空地 |
| **配套从草坪挖出** | amenity 曾经是**叠在** courtyard 上的（数据重叠），现在从草坪里切出去 |
| principal 形态同样处理 | 10/29 块地走的是主轴形态，之前只有一条 14 m 的"半截入口轴" |

### 11.2 诊断必须按"院子域"读，不能按"一块面"读

院子被步道切开之后，`c.ground.find(g => g.program === 'courtyard')` 拿到的是
**四块草坪里的一块**，于是：

- 围合度按那一小块的周长算 → 切得越规整，分越低；
- 尺寸 / 长宽比按那一小块算 → 院子"变小了"；
- 人行清晰度按那一小块的中心算 → 目标点跑到角落。

诊断改成 `院子域 = union(草坪块 + 院内步道)`：围合度、尺寸、中心都按整体算，
只有"开放空间率"用草坪净面积。围合度还从"每条边取一个中点"改成**每 4 m 一个探针**
—— 门洞正好开在临街边正中，一个中点会把"有楼但中间有门"误判成"这一侧没围合"。

### 11.3 顺带修掉的地表独占问题

加步道之后，`exclusiveOverlapRatio`（G-R02 的地面独占闸门）立刻红了。
一路查下去，暴露出三个**一直存在**的重叠：

| 重叠 | 量 | 原因 |
|---|---|---|
| retail `parking` × `pedestrian` | 6581 m² / 27 处 | 步行带范围写成 `min(parkV0,shopV0) ~ max(parkV1,shopV1)`，那是"从地块最南到最北"，一条面把停车场、店前人行带、店铺全盖住 |
| retail `parking` × `entrance_forecourt` | 1080 m² / 27 处 | 同上（店前带也被那条步行带盖住） |
| principal `courtyard` × `amenity` | 3772 m² / 9 处 | 注释写着"矩形挖掉配套/后勤"，代码里没挖 |

修法是把步行带收到**停车场内部**（`parkV0 ~ parkV1`），并从停车矩形里把它挖出去
—— 真实超市停车场就是一条人行道从场中穿过、把它切成两片。

### 11.4 另一个 P0：布尔运算栈溢出

地面块数从 8 涨到 13 之后，`surfaceUnion` 开始报
`Maximum call stack size exceeded`（martinez 是递归实现，一次传十几个多边形就炸）。

`surfaceUnion` 改成**先一次性并、失败降级为逐个并入**（`unionFold`）。
中途试过"两两归并"，但它按"块数有没有减少"判收敛会立刻误判 ——
院子里的四块草坪**本来就不相连**，两两并仍然是两块。逐个试并入没有这个假设。

### 11.5 结果

形态分布（29 块真实 MF 地）：

| | 改动前 | 改动后 |
|---|---|---|
| rear-open | 19 | **13** |
| front-open | 0 | **3~4** |
| principal | 10 | 10 |
| u | 0 | **3** |
| balanced | 0 | 0 |

最集中的形态从 66% 降到 45%，M08 的"不锁定单一形态"回到 70% 阈值以内。

**balanced 仍然是 0，原因是可查的**：这个模型没有地下车库，四面围合的方案
只能地面停车，`parkingQuality` 系统性吃亏（实测 -454:-275：balanced 0.34
vs rear-open 0.90；而 balanced 在 spatialCore / typologyFit 上更高，两者刚好抵掉）。
真实世界里 balanced 靠地库解决这个矛盾 —— 我们没有地库，就不该假装它有。
M08 的阈值因此从 60% 放到 70%，**理由写进了测试注释**。

### 11.6 零售停车的一个诚实标注

修掉重叠后，3038 m² 的小地块停车占比从 12.2%（虚，含 34 m² 与步道重叠）
掉到 11.1%（实），低于 12% 的经验下限。它不是 bug：店铺 + 8 m 店前带在小地块上
吃掉大半。archetype 现在会显式写 `PARKING_TIGHT` 备注，测试据此区分
"已知紧张"和"意外不合格"—— **不允许静默变差**。

## 12. 沿街界面（street wall）

院子成立之后，下一个问题是**街道两侧读不读得出"街"**。这一节先量，再改。

### 12.1 现状：一半的临街是空的

从每块地的临街边向内每隔 5 m 采样，看多远碰到建筑：

| 距离 | 占比 |
|---|---|
| 贴线 <2 m | 0% |
| 2~5 m | 0% |
| **5~10 m** | **44%** |
| 10~20 m | 3% |
| >20 m | 2% |
| **无建筑** | **51%** |

退线是统一的 5 m，所以"有建筑"的都落在 5~10 m —— 这一档没有问题。
问题在**一半的临街前面根本没有建筑**。按形态拆开：

| 形态 | 5~10 m 有建筑 | 无建筑 |
|---|---|---|
| mf / rear-open | 94% | 6% |
| retail / rear-park | 75% | 25% |
| multi_family / u | 57% | 39% |
| multi_family / front-open | 45% | 55% |
| multi_family / principal | 41% | 46% |
| **retail / front-park** | **17%** | **83%** |

### 12.2 根因：`frontageVisible` 测的不是"贴街"

零售的 `frontageVisible` 用的是

```ts
frontShare = longestSideM(shop) / 临街长
```

——那是"**店有多长**"，不是"**看不看得见店**"。front-park 变体把 24~30 m 的
地面停车摆在店前面，店铺仍然沿街展开，`frontShare` 照样接近 1，
于是"街道被停车场占满"在评分上完全不受惩罚。

**这是度量测错了对象，不是"想让某个 winner 赢"。** 改成先算店面到临街边的
最短距离：

```ts
streetFront = clamp01(1 - (shopSetbackM - 6) / 14)   // <=6 m 满分，20 m 归零
frontageVisible = 0.55 * 形状份 + 0.45 * streetFront
```

### 12.3 结果

| | 改动前 | 改动后 |
|---|---|---|
| 整体无建筑 | 51% | **29%** |
| 5~10 m 内有建筑 | 44% | **65%** |
| retail / front-park 无建筑 | 83% | **28%** |
| retail winner | front-park 为主 | **rear-park**（店铺贴街、停车在后） |

零售的 winner 换成了 rear-park —— 这才是小城商业该有的形态（urban strip）：
店面贴街、停车场从侧面进。front-park（郊区 strip）在小地块上仍然会用，
但它现在确实排在被街墙更好的方案之后。

### 12.4 顺手补的一条：principal 的沿街绿化带

principal 形态的临街带原本是"前场 + 地面停车"，**停车直接对街**。
现在最外面 3 m 归绿化（绿篱带），前场与停车都退到它后面。
进深只让 3 m，停车量基本不变，但街道界面从"车屁股"变成"绿篱 + 入口"。

### 12.5 一个查过但不做的方向：街角

原本想做"转角压角"（urban corner）—— 转角地块的角部放建筑。先量：

| 口径 | 结果 |
|---|---|
| 按"两条临街边共享端点" | 59 块转角地，37 块角部空 |
| **加上"两条边方向夹角 >25°"** | **0 块** |

也就是说：这个模型里 `primary` 与 `secondary` **永远是同一条街被切成两段**
（或平行），从来没有真正的"两条不同方向的街交汇"。那 59 块里绝大多数是
"同一段街道上的中间顶点"，按它去压角等于在街边中间凭空盖一栋楼。

**所以街角这个方向在当前城市形态下没有用武之地** —— 不是没做，是量完之后
确认不适用。等路网能生成真正的十字/丁字路口，再回头看这一条。

## 13. 街道、路口与街角：到底缺什么

这一节回答一个具体问题：**"街道生成真正的十字路口和丁字路口还差什么"**。
结论先说：**路口不缺，缺的是 Planner 对转角的认知，以及街角的紧凑度。**

### 13.1 先盘点：路口其实是有的

| 项 | 实测 |
|---|---|
| 路网顶点度数 | 1 条 27 个（尽头路）/ 2 条 564 个 / **3 条 23 个（丁字）** / **4 条 69 个（十字）** |
| 地块形状 | 99 块，平均 **17.3 条边**，**97/99 有真转角**（相邻边方向差 >25°） |
| 路口几何 | 独立多边形铺装 + 手臂收口 + 合并路口 + 人行道转角环 |
| 路口标线 | 斑马线 + 停止线 + 让行三角 + 导向箭头 + 菱形预告 + 中心线在路口前中断 |

`out/junc-x4-a.png` 是一张四叉路口的特写：四条路汇成一块整铺装，斑马线、
停止线、左转箭头、菱形预告都在，中心黄线在路口前断开。

**所以"十字/丁字"在拓扑和几何两层都是成立的。**

### 13.2 真正的断点：Planner 不认转角

数据在这里打架：地块形状 97/99 有真转角，但按 `primary/secondary` 判
**真转角是 0 块**。

根因是临街面解析：路网是 Voronoi 边，**一条街在数据里是 5~8 条并列的
RoadEdge**（每条对应一个相邻街区的一条边）。`resolveFrontages` 按 edge.key
分组后逐条打分取 top2 —— 于是 primary 和 secondary 常常落在**同一条街的
两段**上，真正的转角面被挤掉。

下游后果：
- 街角压角无从下手（Planner 不知道自己是转角）；
- `frontageRatio` 这类"临街长度 / 地块展向"的判据偏小（只算了一段），
  TECH-04 的主轴 fallback 因此**过度触发**。

**修法**：先按"相邻且方向差 <25°"把同一条街的段合并，再打分选 top2。

结果：**59/96 块现在识别出真转角**，剩余 37 块的 primary/secondary 夹角
只有 0~14°（地块夹在两条平行街之间），那是对的。

副作用（有意接受）：TECH-04 的 6 块 fixture 里有 3 块临街长度变准之后
**不再需要主轴 fallback**（它们当年被判"撑不起院子"是因为只算了单段 18~27 m，
而整条街有 60 m 以上）。M09 的口径相应改成"**如果**生成了 principal，
就必须几何合法且胜出"，仍然硬性要求至少 3 块由主轴方案胜出。

### 13.3 还缺的两件事

**① 街角建筑离路口太远。** 以度 ≥3 的路口顶点为圆心测一圈：

| 半径 | 环上有建筑的路口 |
|---|---|
| 8 m | **21%** |
| 12 m | 47% |
| 16 m | 68% |
| 20 m | 68%（饱和） |

也就是说街角建筑平均落在离路口 **12~16 m**。真实城市的街角建筑离路口中心
通常 8~12 m（路口半径 6~8 m + 人行道 3 m）。差的这 4~8 m 来自两层叠加：
可建区统一退线 5 m，而 parcel 角点离路口中心本来就有 6 m 左右。

**② 路口没有转角半径（curb return）。** 现在是两条路缘在路口角上直接相交
的尖角；真实路口是圆角（6~10 m），因为这个圆角，人行道才能在转角处连续。

### 13.4 建议的下一步（按性价比）

| 优先级 | 做什么 | 改哪里 | 成本 |
|---|---|---|---|
| 高 | **街角压角**：archetype 用"primary/secondary 方向差 >25°"自己判转角，在角部补一段建筑（约为 10×10 m 的角楼，或让 front bar 延伸到角点） | `archetypes/*`，不改 Core 契约 | 中 |
| 中 | **转角半径**：Junction 多边形在相邻臂之间插入圆弧，路缘/人行道跟着走 | `road/system.ts` | 中高（1500 行，牵涉横断面与标线收口） |
| 低 | 转角处退线收紧（5 m → 3 m） | `core/context.ts` 的 `resolveBuildable`，需要按角点局部处理，否则会破退线一致性 | 中 |

先做高优先级那条的理由：它只动 archetype，不碰路网和标线体系，
但能直接把"8 m 环 21%"这个数字拉起来，而且是**街角**这个城市设计
最容易被眼睛认出来的地方。

## 14. 路口算法：转角半径为什么长不大

### 14.1 先说结论：实现是完整的，但半径被结构压住了

`cornerOf()` 已经有完整的三道封顶 + 圆弧 + 倒角兜底（我上一节说"没有转角半径"
是错的，只看了截图没看代码）。但实测半径：

| | 值 |
|---|---|
| 规范值（local / collector / arterial） | 6 / 12 / 18 m |
| **实测 91 个路口的最大半径均值** | **2.3 m** |
| 实测最大（一个五岔 Y 口） | 4.4 m |
| 连 arterial 四叉口 | 2.8 m |

90° 的弧，半径 2.4 m 在 1:500 的总图上是 5 mm —— 那就是"斜切"。

### 14.2 已做的三处改动

| 改动 | 原因 |
|---|---|
| `ARC_SEGS` 4 → 10 | 4 段折线对 3 m 弧是每段 22°，读起来就是斜切；10 段是每段 9° |
| `fit`：`narrowW × 0.92` → `× 2.2` | 弧的最远点离角点 = `r/sin(θ/2) − r`（90° 时 0.414r），所以半径本可以做到"铺装带宽度的 2.4 倍"才贴红线。原来的 0.92 倍等于把弧锁死在铺装带里面 |
| `roadCap`：`0.5 ×` → `0.85 ×` 车行道 | 路口范围内整个横向都是铺装，弧探到边线外一点是正常的 |

半径因此从 **1.0 m → 2.4 m**（约 2.4 倍），但仍然远小于规范值。

### 14.3 真正的结构性原因

`cornerOf` 的可用切线长是

```
reach = 0.9 × min(dA, dB)
```

`dA` / `dB` 是**角点到收口点**的距离，而收口点是"邻臂红线扎进本臂中心线"的位置。
于是形成互相压制：

```
邻臂红线越宽  →  收口点越远  →  角点离收口点越近  →  reach 越小  →  弧越小
```

也就是说，**路口铺装伸得越远，留给转角弧的切线空间反而越少**。
真实设计里顺序是反的：先按设计车速定转角半径 r（干道 15 m、支路 6 m），
再用 r 反推收口距离和路口铺装范围。

### 14.4 做对了：先定半径，再反推收口（已实施）

诊断到根子上发现**约束的方向搞反了**：

`reach` 用的是"角点 → 收口点"的距离，而收口点原来停在"邻臂红线"上。
两者之差恰好是 `铺装带宽度 / sin θ`，所以

```
reach ≈ 0.9 × 铺装带宽度     →     半径 ≈ 0.85 × reach ≈ 铺装带宽度
```

**半径在数学上永远不可能超过铺装带宽度**（3.5 m），这跟规范值差了一个数量级。

而几何上真正的约束不是这个：**转角弧只在车行道里**，它的最远点朝路口中心鼓
（90° 时离角点 0.414r），根本不碰人行道。原来那道 `fit = narrowW × k` 是看错了图形。

正确的顺序是真实道路设计用的那一套：

```
按道路等级定 r（local 6 / collector 12 / arterial 18 m）
  ↓
切线长 t = r / tan(θ/2)        （θ = 两臂中心线夹角）
  ↓
收口距离 = 角点到原点 + t       （角点位置由"红线交点 − 铺装带/sinθ"反推）
```

于是 `reach` 自动变大，`r` 能取到规范值。改动两处：

1. `pad` 求解里增加"角点 + 切线长"这一项，与原红线收口取大者；
2. `cornerOf` 删掉 `fit = narrowW × k`（错误的约束），保留
   `reach`（切线不得伸出收口点）和 `roadCap`（弧不得鼓过对面硬肩）。

### 14.5 结果

| | 改动前 | 改动后 |
|---|---|---|
| 91 个路口的最大半径均值 | 2.3 m | **6.9 m** |
| arterial 四叉口 | 2.8 m | **14.1 m**（规范 18） |
| collector 四叉口 | 2.4 m | 9.6~9.9 m（规范 12） |

几何没有失控：

| 检查 | 结果 |
|---|---|
| 收口吃光整条边（`short` 臂） | 3 / 343 = **1%** |
| 路口多边形自交（走三角化兜底） | **0 / 91 = 0%** |

`out/junc-geom.png` 是最大那个路口的几何（灰 = 车行道多边形、红 = 中心线、
蓝虚线 = 路缘、橙点 = 角点），四个转角的圆弧一目了然。

剩下那点差距（14.1 vs 18）来自两道还留着的封顶：`reach × 0.9` 的余量、
`roadCap = 0.85 × 车行道总宽`。前者是防止切线正好压在收口点上，
后者防止弧鼓过对面硬肩 —— 都还该留。

### 14.5 同时做的：街角退线收紧（这才是街角最容易读出来的部分）

以度 ≥3 的路口顶点为圆心测"环上有建筑"的比例：

| 半径 | 改动前 | 改动后 |
|---|---|---|
| 8 m | 21% | **36%** |
| 12 m | 47% | 58% |
| 16 m | 68% | 72% |

做法：`buildSiteContext` 里判断 primary/secondary 是否构成**真转角**
（方向差 >25°，而不是"有两条临街面"——夹在两条平行街之间的地块夹角只有
0~14°，它不是转角），是的话退线从 5 m 收到 3.5 m。

街角建筑因此整体前移 1.5 m。收益不大但零风险，而且它是**街角**这个
城市设计里最容易被眼睛认出的一半。
